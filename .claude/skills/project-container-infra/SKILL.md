# Project Cloud Run infra.tf generator

## Ground truth

- There is exactly **one** shared GCP environment for the whole repo: `module.shared_environment` in [99_shared-infra/main.tf](../../../99_shared-infra/main.tf), backed by [99_shared-infra/modules/gcpEnvironment](../../../99_shared-infra/modules/gcpEnvironment/main.tf) — project `mk-ai-projects` (number `655315820279`), region `us-central1` by default, with the Cloud Run API enabled once for the whole project.
- Every `project_<name>/infra.tf` deploys a `google_cloud_run_v2_service` into that shared project/region using its **own** `var.gcp_project_id` / `var.gcp_region` (declared in `variables.tf`, defaults `mk-ai-projects` / `us-central1`) — **not** a `terraform_remote_state` read from `99_shared-infra`. `99_shared-infra` itself reads *this* project's state (for the Cloudflare CNAME target — see `terraform-infra-gen`), so a reverse read here would be circular: neither side's state exists on a fresh checkout, so `terraform plan` on either would fail with "no stored state found" forever. project_id/region are static config known upfront, not something generated by applying shared-infra, so don't chain them through remote state.
- **Never** create a new GCP project or re-enable APIs inside a `project_*` directory. If a project genuinely needs isolation (its own project/billing), that's a module-contract change — stop and ask MK explicitly before touching `modules/gcpEnvironment` or `modules/gcpCloudRun`.
- Each `project_<name>/` directory has **three** files, split so per-project values live in exactly one place:
  - `infra.tf` — static, identical shape across all projects, references `var.*`
  - `variables.tf` — static, declares those vars with the module's defaults
  - `app.tfvars` — the ONLY file with project-specific values (name, image, port, cpu, memory, instance counts)
- Templates for all three live in [99_shared-infra/templates/](../../../99_shared-infra/templates/): `project-infra.tf.tmpl`, `project-variables.tf.tmpl` (copy both as-is, no placeholders), and `project-app.tfvars.tmpl` (has the `{{PLACEHOLDER}}`s to fill in). Keep them in sync with `99_shared-infra/modules/gcpCloudRun/variables.tf` if that module's contract ever changes.
- Because `app.tfvars` isn't named `terraform.tfvars` or `*.auto.tfvars`, every `plan`/`apply` needs `-var-file=app.tfvars` explicitly. `validate` doesn't need it.
- Auth is via Application Default Credentials (`gcloud auth application-default login` or `GOOGLE_APPLICATION_CREDENTIALS`) — never hardcode a service account key path in any `.tf` file.
- Images: default assumption is a public Docker Hub image (`docker.io/<user>/<project-name>:latest`), pulled directly by Cloud Run with no registry credentials needed. If a project needs a private image, that requires an Artifact Registry repo + IAM — a module-contract change, ask MK first.
- Access control: `allow_unauthenticated` (default `true`) grants `roles/run.invoker` to `allUsers`. Set it `false` and list `invoker_members` (e.g. `["user:you@example.com"]`) to restrict to specific principals instead — but know that restricting access also breaks plain browser access to any mapped custom domain, since browsers don't send the required Google identity token. Confirm with MK which they want; don't default to restricted without asking.
- Custom domains: set `custom_domain` (e.g. `"mk-stock-screener.mayankkoli.com"`) to create a `google_cloud_run_domain_mapping` (Preview) — this is what makes Google's edge recognize the custom host at all. Without it, a Cloudflare CNAME pointed at the raw `*.run.app` URL will resolve but fall back to Google's default page, because the Host header won't match anything Cloud Run knows about. **Prerequisite Terraform can't do for you**: the domain must already be verified for `mk-ai-projects` in [Search Console](https://search.google.com/search-console) under the identity running `apply` — tell MK to do this manually before `apply` if it's not done yet, `terraform plan` will still succeed but `apply` will fail on the mapping resource without it.
- The module outputs `domain_mapping_cname_target` (the CNAME Cloudflare must point at — `ghs.googlehosted.com` for subdomains) when `custom_domain` is set; `null` otherwise. `terraform-infra-gen` reads this via remote state — don't use `uri` for the Cloudflare target once a domain mapping exists.
- `deletion_protection` (default `false` in the module) is Cloud Run v2's own guard against accidental `terraform destroy`. Left off by default since these are single-owner prototype projects iterated on frequently. If a failed/tainted apply ever leaves a resource with the *old remote* value stuck at `true`, plain `destroy` errors even after this default is fixed locally — see the tainted-resource recovery note below.
- Azure Container Apps code (`azureContainers`, `azureEnvironment` modules and the old per-project Azure `infra.tf`s) is retired — archived under [archive/azure/](../../../archive/azure/), not wired into any `main.tf`. Don't resurrect it without MK asking explicitly.

## Non-negotiable rules

1. **Default to `plan`/`fmt`/`validate` only.** This repo has no CI/PR pipeline yet (no git remote), so unlike a normal setup `apply` doesn't happen elsewhere automatically — MK runs it themselves, or explicitly asks you to run it in the moment. Never run `apply` on your own initiative; always be asked for that specific action.
2. If this is a git repo with a CI pipeline set up later: work on a branch (`infra/<project-name>`), never commit to `main` directly, open a PR, and go back to never running `apply` yourself.
3. Show the plan (or at minimum a clean `validate`) before calling the task done.
4. **Verify the image tag actually exists before `apply`, every time** — don't trust that a Docker Hub repo existing means the tag does. `curl -s "https://hub.docker.com/v2/repositories/<user>/<repo>/tags?page_size=25"` and grep for `"name"`. A wrong tag (e.g. typo'd `mealplan` vs. actual `mealplan-app`) fails Cloud Run's revision creation, which taints the service resource in state — annoying to unwind (see below), cheap to avoid by checking first.
5. **Don't `rm -rf .terraform` in a directory MK might be applying in concurrently.** It raced against a live `apply` once already (deleted the provider plugin cache mid-run, apply errored on a missing package directory). If MK has a terminal open running plan/apply themselves, ask before cleaning up cache dirs, or just leave them — they're gitignored, harmless to leave around.

## Recovering a tainted/stuck resource

If an `apply` fails mid-creation (bad image tag, missing IAM, etc.), Terraform marks that resource **tainted** — the next plan forces a destroy-and-recreate, and Cloud Run's `deletion_protection` (previously defaulted `true` before this module set it `false`) can block that destroy even after you've fixed the underlying `.tf`/`.tfvars` bug. Don't fight this with manual `destroy`:

1. Fix the actual problem first (correct image tag, etc.) in `app.tfvars`.
2. `terraform untaint module.app.google_cloud_run_v2_service.this` — this turns the next plan back into a plain in-place update instead of destroy+recreate.
3. `terraform plan -var-file=app.tfvars` — should now show `~ update in place` (image fix + `deletion_protection: true -> false`), not `-/+ destroy and recreate`.
4. Apply once MK confirms.

## Process

1. Confirm with MK (briefly, inline): project name (matches the `project_<name>` directory), container image reference, port the container listens on, whether `min_instances=0 / max_instances=1` is still right (it almost always is), public vs restricted access, and the custom domain (if any — and whether it's already verified in Search Console).
2. If `project_<name>/` doesn't exist yet, create it.
3. Copy all three templates:
   ```
   cp 99_shared-infra/templates/project-infra.tf.tmpl project_<name>/infra.tf
   cp 99_shared-infra/templates/project-variables.tf.tmpl project_<name>/variables.tf
   cp 99_shared-infra/templates/project-app.tfvars.tmpl project_<name>/app.tfvars
   ```
4. In `app.tfvars` only, replace every `{{PLACEHOLDER}}`:
   - `{{PROJECT_NAME}}` → the project name (used as the Cloud Run service's `name`)
   - `{{IMAGE}}` → full image ref, e.g. `docker.io/<dockerhub-user>/<project-name>:latest` — verify the tag exists (see rule 4 above) before treating this as done
   - `{{CONTAINER_PORT}}` → the port the container listens on (default 8080)
   - `{{CPU}}` → default `"1"` (Cloud Run vCPU, as a string)
   - `{{MEMORY}}` → default `"512Mi"`
   - `{{MIN_INSTANCES}}` / `{{MAX_INSTANCES}}` → default `0` / `1`
   `infra.tf` and `variables.tf` need no edits — leave them as copied.
5. Run `terraform fmt -recursive` and, inside `project_<name>/`, `terraform init -backend=false -input=false && terraform validate`.
6. Run `terraform plan -var-file=app.tfvars` (full `terraform init -input=false` first, not `-backend=false`, if you're about to also `apply`) and summarize the result in plain language.
7. If MK also wants the project reachable on a subdomain, hand off to the `terraform-infra-gen` skill for the Cloudflare half — it needs this project applied first (reads `domain_mapping_cname_target` from this project's state).
8. `terraform-infra-gen`'s `projects` map entry must be added **immediately after** this project is applied — a Cloud Run service alone doesn't get a Cloudflare record automatically; that's a separate, deliberate step in the other skill. Don't consider a project "fully live" until both halves are done.
